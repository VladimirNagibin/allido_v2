# Инструкции для разработчиков и ИИ-помощника

## Проект и домен

- **Название**: `allido`
- **Описание**: Веб-приложение для хранения, комментирования и рекомендаций событий (спектакли, поездки, экскурсии, кино и т.п.). Поддерживает древовидную структуру событий (головное событие → подсобытия), гибкие права доступа (пользователи, группы, публичные события) и разграничение доступа к частям данных (например, к фото).
- **Основные сущности**:
  - `User` — пользователь.
  - `Group` — группа пользователей (для выдачи доступа на уровне группы).
  - `EventType` — справочник типов событий (`theater`, `excursion`, `trip`, `movie`, ...), хранит JSON-схему специфических атрибутов.
  - `Event` — событие (с `parent_id` для подсобытий, `event_type_id`, `attributes: JSONB`).
  - `EventParticipant` — участие пользователя в событии с ролью (`owner`, `editor`, `viewer`).
  - `EventAccessRule` — правила доступа к частям данных события (`resource_type`, `access_level`, `target_user_id` / `target_group_id`).
  - `Comment` — комментарий к событию.
  - `Attachment` / `Photo` — вложения и фото, привязанные к событию с возможностью ограничения доступа.
- **Ограничения домена**:
  - Иерархия событий — **древовидная**, глубина не ограничена. Подсобытие может быть любого типа, независимо от типа родителя.
  - **Тип события — это данные, а не класс.** Запрещено ORM-наследование событий по типам (single/joined/concrete table inheritance). Специфические атрибуты хранятся в `Event.attributes` (JSONB) и валидируются Pydantic-моделью по коду типа.
  - Все операции, изменяющие состояние (создание, обновление, выдача прав), должны быть **идемпотентными** там, где это применимо (например, повторная выдача того же права не создаёт дубликат).
  - **Проверка прав обязательна на каждом запросе** к событию и к его частям данных. Права наследуются: доступ к родительскому событию даёт доступ к подсобытиям, если не переопределён явно.
  - Строгая асинхронность: никаких блокирующих вызовов (sync I/O) в асинхронном контексте.

### Принятые коды типов событий

| Код (`EventType.code`) | Название (ru) | Специфические атрибуты |
|---|---|---|
| `theater` | Спектакль | `actors`, `director`, `theater` |
| `excursion` | Экскурсия | `route`, `locations`, `guide` |
| `trip` | Поездка | `cities`, `transport`, `accommodation` |
| `movie` | Кино | `film`, `cinema`, `session` |

> При добавлении нового типа — только новая строка в `event_type` + Pydantic-модель + запись в `TYPE_SCHEMAS`. Никаких новых таблиц и миграций.

## Архитектура

- **Слоистая архитектура** (Clean Architecture / Hexagonal):
  - `src/api/` — роутеры FastAPI, зависимости, рендеринг HTMX-фрагментов.
  - `src/services/` — бизнес-логика: работа с деревом событий, проверка прав, оркестрация.
  - `src/repositories/` — абстракции для работы с БД и кэшем.
  - `src/integrations/` — клиенты внешних API (геокодеры, календари, рекомендательные сервисы).
  - `src/web/` — Jinja2-шаблоны и HTMX-партиалы.
- **Зависимости**: допустимы только сверху вниз (API → Services → Repositories/Integrations). Репозитории и интеграции не должны знать о сервисах.
- **Внедрение зависимостей (DI)**: использование `fastapi.Depends` и контейнеров зависимостей.
- **Работа с данными**: Репозитории работают через `SQLAlchemy 2.0` (async) и `redis.asyncio`.
- **Транзакционность**: управление сессиями БД через middleware или dependency injection (паттерн Unit of Work).
- **Кэширование**: кэширование дерева событий и результатов проверки прав реализуется на уровне сервисов или репозиториев с использованием Redis. Инвалидация — по `event_id` и `user_id`.
- **Дерево событий**: выборка поддерева — через рекурсивный CTE в PostgreSQL. Материализованные пути (`path`) допустимы как оптимизация, но не как замена `parent_id`.

## Стандарты кодирования

- **Форматирование и линтинг**: `black`, `ruff` (настройки из `pyproject.toml` включая `ruff format` и проверку импортов), `mypy --strict`.
- **Типизация**: использование современных конструкций Python (PEP 604 `X | Y`, PEP 585 `list[X]`). Избегать `typing.Optional`, `typing.List` в пользу встроенных типов (все функции и методы аннотированы).
- **Нейминг**: осмысленные имена, отражающие бизнес-логику. Избегать аббревиатур, кроме устоявшихся (API, DTO, ID).
  - Переменные, функции, методы: `snake_case`
  - Классы: `PascalCase`
  - Константы: `UPPER_SNAKE_CASE`
  - Приватные методы/атрибуты: с префиксом `_` (один подчёркивание)
- **Логирование**: структурированное логирование через `python-json-logger`. Обязательные поля в каждом логе:

```json
{
  "asctime": "2026-05-11T17:06:48",
  "levelname": "INFO",
  "name": "events",
  "module_name": "/app/src/services/event.py",
  "class_name": "EventService",
  "method_name": "create_sub_event",
  "message": "Sub-event created under parent.",
  "event_id": 42,
  "parent_id": 7,
  "user_id": 3
}
```

  - Дополнительные поля (необязательные) могут быть добавлены через параметр `extra` в вызове логгера. Для событий домена рекомендуется всегда добавлять `event_id`, `user_id`, `parent_id` (если применимо).
  - Конфигурация должна обеспечивать автоматическое добавление `asctime`, `module_name`, `class_name`, `method_name`. Для этого используется кастомный форматтер.

## Документация и комментарии

- **Докстринги** (тройные двойные кавычки) — **на русском**, содержат краткое описание, аргументы, возвращаемое значение, исключения.
- **Комментарии внутри кода** — **на русском**, поясняют сложную логику.
- **Логи и сообщения исключений** — **на английском**.

## Обработка ошибок

- **Базовое исключение**: все кастомные исключения наследуются от `BaseAppException` (расположен в `src/core/exceptions/base.py`).
- **Содержательность исключений**: каждый класс исключения должен определять:
  - `error_code` — строковой код ошибки (например, `"EVENT_ACCESS_DENIED"`),
  - `message` — человекочитаемое описание (на английском),
  - `status_code` — HTTP-статус (опционально),
  - `details` — дополнительные данные (опционально, dict).
- **Доменные исключения AllIDo** (минимум):
  - `EventNotFound` — событие не найдено.
  - `EventAccessDenied` — нет доступа к событию или его части.
  - `EventTypeUnknown` — неизвестный код типа события.
  - `EventAttributesInvalid` — атрибуты не прошли валидацию по схеме типа.
  - `EventCycleDetected` — попытка сделать событие подсобытием своего потомка.
  - `GroupNotFound`, `UserNotFound`.
- **Глобальный обработчик**: в `src/main.py` функция `configure_exception_handlers` регистрирует обработчик `BaseAppException`, который формирует стандартизированный JSON-ответ.
- **Формат ответа API при ошибке**:

```json
{
  "error_code": "EVENT_ACCESS_DENIED",
  "message": "User has no access to event photos.",
  "details": {"event_id": 42, "resource_type": "photos", "user_id": 3},
  "request_id": "8f3e2d1c-..."
}
```

- **Не подавлять исключения без необходимости**: логировать с уровнем ERROR.

## Типовые задачи для ИИ

1. **Ревью предложений изменений в коде**
   - Проверять соответствие архитектуре, кодстайлу, типизации.
   - Отдельно проверять **корректность проверок прав доступа** — это критичная зона.
   - Указывать на потенциальные проблемы производительности (N+1 при обходе дерева) или безопасности.

2. **Генерация unit-тестов**
   - Использовать `pytest` и `pytest-asyncio`.
   - Обязательно покрывать тестами: проверку прав (позитив/негатив), работу с деревом событий, валидацию атрибутов по типу.
   - Репозитории тестировать с in-memory БД или моками.
   - Стремиться к покрытию ≥80%.

3. **Генерация кода**
   - Соблюдать все перечисленные стандарты.
   - Для новых эндпоинтов создавать Pydantic-схемы в `src/schemas/`.
   - Для новых таблиц — модель SQLAlchemy, alembic-миграцию и репозиторий.
   - Для новых типов событий — регистрировать `EventType` + Pydantic-модель атрибутов в `src/schemas/event_attributes/`, **без новых таблиц**.
   - Всегда добавлять тесты на новый функционал.

4. **Написание миграций (Alembic)**
   - Генерировать миграции через `alembic revision --autogenerate`.
   - Проверять, чтобы миграции были идемпотентными (обратимыми).
   - Для JSONB-полей проверять корректность индексов (GIN) при необходимости.

5. **Оптимизация SQL-запросов**
   - Устранение проблемы N+1 при загрузке поддерева (использовать `selectinload` / рекурсивный CTE).
   - Предложение индексов: `event(parent_id)`, `event(event_type_id)`, GIN по `event.attributes`, `event_access_rule(event_id, resource_type)`.

## Чего делать не нужно (Антипаттерны)

- **Не использовать ORM-наследование для типов событий.** Только `Event` + `EventType` + `attributes: JSONB`.
- **Не делать `parent_id` без проверки на циклы.** При перемещении события обязательно проверять, что новый родитель не является потомком.
- **Не хранить права доступа только в коде.** Все правила — в БД (`event_participant`, `event_access_rule`), чтобы их можно было менять без деплоя.
- **Не использовать синхронные библиотеки** (`requests`, `psycopg2`, `time.sleep`) внутри `async def`. Блокирующий код запрещён (используйте `asyncio.to_thread` при необходимости).
- **Не менять сигнатуры публичных API** (роутеров, интерфейсов сервисов) без явного запроса.
- **Не переписывать работающий код «ради красоты»**, если это не несёт практической пользы.
- **Не использовать "голые" исключения** (`except Exception:` или `except:`) без логирования и проброса.
- **Не хардкодить конфигурации**, секреты и URL — использовать `pydantic-settings` и переменные окружения.
- **Не создавать циклические импорты** между слоями.
- **Не игнорировать типизацию** — `# type: ignore` только в крайнем случае с комментарием причины.
- **Не рендерить на клиенте то, что можно отрендерить на сервере.** HTMX-подход: сервер отдаёт готовый HTML-фрагмент, клиент только вставляет его в DOM.

## Дополнительные рекомендации

- **Асинхронность** везде, где это возможно: все эндпоинты, сервисы, репозитории — `async def`.
- **Переменные окружения** читать через `pydantic-settings.BaseSettings` (файл `.env` не коммитить).
- **Миграции** применять через `alembic upgrade head` при деплое.
- **HTMX-контракт**: каждый эндпоинт, возвращающий фрагмент, должен иметь понятное имя шаблона-партиала и, при необходимости, использовать `hx-swap-oob` для обновления нескольких областей.
- **Права доступа**: любая новая фича, работающая с данными события, обязана вызывать сервис проверки прав. Ревью без этого — блокирующее.
- **Коммиты**: атомарные, с осмысленными сообщениями на русском или английском (единообразие).
- **Pull Request**: перед созданием убедиться, что все тесты проходят, линтеры и mypy не выдают ошибок.
